# DATA-01: синтетические данные

Версия каталога и условий: `synthetic-v1`. Все товары, цены, остатки,
документы, сертификат, IDs посетителя и корзины вымышлены. Они не описывают
ассортимент или обязательства ekt.kz. Ссылки `example.invalid` намеренно
не открываются в сети; содержимое источников и сертификат включены в репозиторий.

## Проверка

Из корня, Python 3.9+ без дополнительных пакетов:

```sh
./scripts/validate-demo-data.sh
```

Валидатор проверяет обязательные поля, уникальные IDs и нормализованные SKU,
decimal-строки, категории/единицы/шаг, статусы остатков, доступные склады,
совместимость, арифметику вариантов, ссылки, контрольные суммы и сигнатуры
файлов. Он также проверяет XML Office Open XML и отклоняет отдельные
негативные примеры. Это проверка данных, а не реализация импорта или OCR.

## Стабильные значения для D1 и D3

| ID | SKU | Сценарий | Доступно |
| --- | --- | --- | --- |
| `1001` | `000001` | Исходный автомат C16, 1P | 12 pcs |
| `1002` | `000002` | Совместимый аналог для дополнения | 8 pcs |
| `1003` | `000003` | Совместимая полная замена | 20 pcs |
| `1004` | `000004` | Похожий автомат C32, несовместимый ток | 100 pcs |
| `1005` | `000005` | Нет в наличии, аналоги 1001/1002/1003 | 0 pcs |
| `1006` | `000006` | Остаток неизвестен | null |
| `1007` | `000007` | Неизвестно напряжение; нельзя объявлять совместимым | 100 pcs |
| `1013` | `000013` | Кабель, дробное количество | 37.5 m |
| `1035`, `1036` | `Aa`, `BB` | Коллизия Java `String.hashCode()` | разные товары |
| — | `999999` | Отсутствующий SKU | NOT_FOUND |

Цена `1001` — `1500.00 KZT`. Все цены указаны за единицу.
У `1001` также есть **недоступный** склад `CLOSED` с остатком 999.
Его нельзя прибавлять к доступным 12. Склады не объединяются без политики
fulfillment; примеры 12+8 и whole20 используют только `ALA`.

Автоматы/лампы: `pcs`, минимум 1, шаг 1. Кабель: `m`, минимум 0.5, шаг 0.5.
Неизвестные quantity/unit в документах остаются `null`, а не 1/pcs.
Условие совместимости — одинаковые категория, единица и **все** обязательные
характеристики. Это правило синтетического набора, не экспертная сертификация.

## Контракт передачи

IDs и артикулы — строки, чтобы сохранить bigint и ведущие нули. Деньги и
количества — десятичные строки; backend читает их в `BigDecimal`. Нормализация
SKU — `trim + uppercase`; исходный `article` сохраняется. `UNKNOWN` и `ON_ORDER`
не имеют известного количества. `OUT_OF_STOCK` имеет точный ноль.

Формат — **DATA-01 draft**, не публичный HTTP DTO. FOUND-01 ещё не реализован
в исходном checkout, поэтому согласование Java ports/OpenAPI с D1 остаётся
точкой передачи. D1 и D3 должны читать этот набор и сохранить его IDs и
значения. Сгенерированный frontend SDK и его типы здесь не менялись.

`terms.json` содержит исходный текст и постоянный `id`/`version`; ответы
проверяются через `terms-answers.json`. `sourceUrl` — ярлык происхождения,
не инструкция скачать URL. Приватных пользовательских документов нет.

## Ожидаемые сценарии

1. AC-1: `000001` → 1001, C16/1P/230V, 1500.00 KZT, 12 pcs, synthetic certificate.
2. AC-2: `000005` → нулевой остаток, совместимые аналоги 1001/1002/1003.
3. AC-3: ответы об оплате/доставке/минимуме цитируют `payment`/`delivery`/`minimum`, v1.
4. AC-4: предложение 2 pcs товара 1001 без отдельного согласия не меняет корзину.
5. AC-5: после отдельного подтверждения существующие 3 + добавляемые 2 = 5 pcs, сумма 7500.00 KZT.
6. AC-6: запрос 20 при наличии 12; после stock12→7 требуется пересмотр предложения, без молчаливого уменьшения.
7. AC-7: ссылка из будущего адаптера корзины должна показывать серверный snapshot из `cart-snapshots.json`.
8. AC-8: `999999` отсутствует; похожий товар не считается найденным SKU.
9. AC-9: выбор `12 × 1001 + 8 × 1002` или `20 × 1003` предшествует отдельному подтверждению.
10. AC-10: result set `[1001,1002,1003]`; «первые два» означает `[1001,1002]`.
11. AC-11: одинаковые три строки в XLS/XLSX/DOC/DOCX/текстовом PDF; JPEG/сканы требуют review.

Эти файлы задают ожидания, но сами не доказывают работоспособность чата,
корзины, импорта, распознавания или deployed приложения.

## Происхождение файлов и обновление

Файлы созданы специально для этого репозитория: XLSX — Artifact Tool,
DOCX — python-docx, PDF — ReportLab, изображения — Pillow.
XLS и DOC конвертированы из соответствующих современных форматов LibreOffice.
В `mixed.pdf` одни и те же три строки встречаются на обеих страницах;
`expectedRowOccurrences: 2` фиксирует это для будущего extraction-теста.
`product-only.jpg` — схематичный синтетический корпус без маркировки;
он не является реальной фотографией и не доказывает качество vision.

Обычному разработчику достаточно готовых файлов и валидатора. При намеренном
обновлении набора:

```sh
python3 scripts/generate-demo-data.py
# Python с python-docx, reportlab, Pillow:
python3 scripts/generate-attachment-fixtures.py
# Node с доступным пакетом @oai/artifact-tool:
node scripts/generate-workbook-fixture.mjs "$PWD"
# soffice — разрешённый headless LibreOffice (в Codex: bundled runtime):
soffice --headless --convert-to 'doc:MS Word 97' --outdir data/attachments/office data/attachments/office/specification.docx
soffice --headless --convert-to 'xls:MS Excel 97' --outdir data/attachments/office data/attachments/office/specification.xlsx
python3 scripts/update-fixture-manifest.py
./scripts/validate-demo-data.sh
```

Повторная генерация бинарных файлов может менять metadata/timestamps и SHA-256.
Контрольные суммы обновляют **после** проверки нового содержимого; валидатор
никогда не переписывает ожидаемые значения. Генераторы не нужны backend runtime.

Для DATA-01 проверены: валидатор, чтение Office Open XML, конвертация DOC/XLS,
визуальный рендер документов/PDF и сохранение SKU/дробного количества.
OCR/vision и integrated agent evaluation выполняются позже в ATT/QA-02.
